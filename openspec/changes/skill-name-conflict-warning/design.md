## Context

`scan()`（skill_registry.py 行 12-24）遍历发现的 `SKILL.md`，对每个计算 `name`（frontmatter 优先，缺失回落 `skill_md.parent.name`），然后 `_index[name] = (description, str(skill_md))`。dict 赋值天然「后写覆盖」——同名时先写的条目被无声替换，且替换结果取决于遍历到达顺序。

`skill-nested-scan` change 会把发现范围从一级目录扩到任意层级，`rglob` 的返回顺序不保证跨平台稳定，使「谁覆盖谁」更不可预测。冲突告警与确定性选定正适合在此 change 统一收口。

约束（CLAUDE.md）：禁止 AI 框架；禁止全局可变状态（路径可 monkeypatch）；mypy strict；行长 100；TDD Hard Gate；测试 skills 目录隔离到 tmp_path。

## Goals / Non-Goals

**Goals:**
- 扫描时检测同名 Skill 冲突并明确报警（含 name 与冲突路径）。
- 用确定性规则选定唯一胜出者，结果与遍历/平台无关。
- 无冲突时索引与对外行为完全不变。

**Non-Goals:**
- 不实现「同名但允许共存/命名空间隔离」——本 change 维持「每个 name 索引唯一」语义。
- 不实现 `exclusive: true` 的运行时询问用户选择（那是多 Skill 共存 change 的范畴）。
- 不改 frontmatter 解析、递归扫描、环境变量名（各自独立 change）。
- 不引入冲突的人工解决流程或 admin 工具（仅报警 + 自动确定性选定）。

## Decisions

### D1：写索引前检测冲突，命中即报警
在 `scan` 中维护「本次扫描已见 name → 已选中的 SKILL.md 路径」的本地状态。准备写入某 name 时，若该 name 已被占用，则判定为冲突，记一条结构化 warning（字段含 `name`、已在索引的路径、新发现的路径）。
**为何**：在写入点检测最直接，能拿到双方路径用于报警；本地状态随 `scan` 调用生命周期存在，不引入模块级可变状态。
**Alternatives**：扫描后对收集到的全部条目做去重检测——被否，需额外缓存所有发现项且丢失「逐个写入」的简单结构，收益不大。

### D2：确定性选定规则 = 路径字符串排序，靠前者胜出
冲突时，比较两个 `SKILL.md` 的路径字符串，取排序靠前者为最终保留条目（无论它是先到还是后到）。
**为何**：路径字符串排序确定、可预测、与文件系统遍历顺序及平台无关；规则简单、可单测、易向用户解释。spec 只要求「按确定规则选定一个」，不规定具体偏好，路径排序是最低惊讶的确定性选择。
**Alternatives**：①保留先到者（first-wins）——被否，「先到」依赖遍历顺序，本身不确定；②按 `version` 高者胜出——被否，version 可能缺失/非语义化，规则复杂且本 change 不应依赖 yaml-frontmatter 的扩展字段（避免跨 change 耦合）；③保留后到者（现状 last-wins）——被否，同样依赖遍历顺序、不确定。

### D3：报警一次，每对冲突都记
对每个被「让位」的同名条目都记一条 warning，确保多重同名（3 个及以上同名）时每次落选都可见，便于排查全部碰撞，而非只报一次。
**为何**：运维需要看到所有被覆盖的 Skill，漏报等于回到静默覆盖。

### D4：无冲突时零行为变化
未发生同名碰撞时，索引内容、`match` / `load` / `list_skills` 输出与引入前完全一致，不产生任何冲突 warning。
**为何**：变更面收敛到冲突场景，最小化对现状的影响与回归风险。

## Risks / Trade-offs

- [路径排序胜出可能与作者「想保留哪个」的直觉不符] → 规则确定可预测且有 warning 提示，作者可据报警调整目录/命名消除冲突；本 change 目标是「不静默覆盖」而非「猜对意图」。
- [与 skill-nested-scan 并行开发，遍历顺序行为相互影响] → 本 change 的确定性选定不依赖遍历顺序（路径排序），两 change 可独立验证；合并后行为完整。
- [回落目录名导致的「意外同名」（不同路径但同目录名）也会触发冲突] → 属预期：它们确实会争夺同一 name 键，报警让作者知情并改用显式 frontmatter `name` 或区分目录名。
