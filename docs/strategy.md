# fleetent 战略背景

> 本文解释 fleetent 为什么存在、面向谁、和竞争对手的差异在哪里。
> 读懂这份文档，你就能理解为什么架构长这样、为什么做某些取舍。

---

## 我们解决什么问题

企业想用 AI 提效，但现有方案都卡在同一个地方：**数据不能出内网，或者治理能力不够**。

- 开源通用平台（LangChain / Dify）：Cloud-first，on-premises 是事后补丁；eval / 审批层几乎没有
- 大厂方案（微软 Copilot）：绑定自家 IM（Teams），数据必须上云
- 重量级 SaaS：私有化部署复杂度极高，客户数据主权问题没解决

真正的空白在于：**开源和大厂都没做好的企业运营层**。

---

## 产品定位

**面向企业 on-premises 部署的 Lean Agent 平台。**

不卖"更强的 AI 能力"——在通用能力上赢不了资源更多的大厂。
卖的是**可信、可治理、可落地的 AI 员工基础设施**。

目标客户：金融、政府、医疗等数据合规敏感行业的技术团队。

---

## 三个差异化方向

### Deploy Anywhere（部署主权）

跑在客户自己的服务器上，数据不出内网。支持 Slack / Telegram / WhatsApp，不绑定特定 IM 平台。单容器部署，零外部依赖，5 分钟内可用。

### Govern Everything（可治理）

每次 agent 运行的 trace、成本、质量打分全部可查。高风险操作暂停等待人工确认（permission gate）。记忆层让 agent 越用越懂业务。从"随机黑盒"变成"可信赖的员工"。

### Adapt Without Code（可适配）

Skill 系统让领域专家写 SKILL.md 就能定制 agent 行为，无需工程师改代码。工程师写工具，领域专家写知识，平台负责组合。

---

## 为什么自研而不是用现有框架

团队在 OpenClaw / Hermes 上的维护成本持续失控（50%+ 工时消耗在平台问题上），两个平台问题数量相当，没有"修好一个就够"的选项。

自研核心逻辑：300 行 agent loop 足够实现完整 tool-use 循环（已通过 mini-agent 项目验证）。自己的代码改得动；别人的 9700 行 monolith，Fork 的技术债不低于重写。

技术哲学：**最少依赖，直接调 SDK，不引入 AI 框架。** LangChain / LangGraph 的过度抽象、频繁 breaking change 和 OpenClaw / Hermes 的问题性质相同，换框架只是换一个维护地狱。

---

## 与 SaaS 团队的关系

| 项目 | 策略 |
|------|------|
| 产品定位 | 互补不竞争：SaaS 团队做云上多租户，fleetent 做 on-premises 企业部署 |
| 代码共享 | 现阶段不耦合——两边都在早期，耦合等于互相 block |
| Skill 库 | 共享维护——本质是 Markdown 文件，一份，两边都用 |
| 记忆 / 评估层 | 稳定后设计为独立 HTTP 服务，两边共调；现阶段各自内嵌 |
